# Decision record

One entry per decision that a reviewer could reasonably have made differently.
Each states the decision, why, what it costs, and what would change it.

---

## 1. Endpoints for unbuilt sprints return 501 rather than not existing

**Decision.** `/documents/upload`, `/chat`, `/search`, `/agents/run` and
`/evaluations/*` are registered with their real authorisation, and their handlers
raise `NotImplementedYetError("Sprint N - ...")`.

**Why.** The frontend and the evaluation harness are written against the API
contract, so the contract needs to exist before the behaviour does. It also makes
the authorisation tests meaningful today: a `501` proves the role check passed and
the handler was reached, a `403` proves it did not — that distinction is the
assertion in `tests/test_authorization.py`.

**Cost.** Endpoints in the published schema that do nothing. Mitigated by naming
the sprint in the error payload.

**Revisit if.** An endpoint slips more than one sprint — at that point remove it
rather than carry a promise.

---

## 2. The database is authoritative for identity; the token is a hint

**Decision.** `get_current_principal` re-reads the user row and their patient
grants on every request. The `role` claim in the JWT is never trusted for
authorisation.

**Why.** A deactivated account or a demoted role must take effect immediately, not
when the token happens to expire. With a 60-minute token, trusting the claim means
a fired clinician keeps clinician access for up to an hour.

**Cost.** One indexed primary-key read plus one grants query per request. At this
scale that is noise; if it ever is not, the answer is a short-TTL cache keyed on
user id with explicit invalidation on role change — not trusting the claim.

**Revisit if.** Profiling shows the lookup is material, which it currently is not.

---

## 3. Chunk text is stored in the database, not only in the vector index

**Decision.** `document_chunks.text` is the system of record. The vector index
holds a copy keyed by chunk id.

**Why.** Plan section 14 requires experiments over chunk size, overlap and
embedding model. Each of those means rebuilding the index. If the text only lived
in the index, every experiment would mean re-running extraction over every
document — slow locally, and billed per page once Document Intelligence is in
play. Keeping the text in SQL Server makes a re-index a pure local operation.

**Cost.** Storage duplication, and two places that can drift. Drift is contained
by treating the database as the source and the index as derived: the index is
only ever written by a rebuild from the database, never edited in place.

---

## 4. Access control lives in application code, never in the prompt

**Decision.** Role, patient scope and sensitivity checks are pure predicates in
`app/security/rbac.py` and `Principal`, with no FastAPI or LLM coupling. The same
functions will gate agent tool dispatch and SQL execution.

**Why.** Plan section 12 requires that instructions embedded in a retrieved
document cannot escalate access. A prompt instruction is a request; a predicate is
a decision. Keeping the predicates framework-free means the identical check runs
whether the caller is a user, an agent step, or the SQL guard.

**Cost.** Some duplication between the HTTP dependency layer and the tool layer.
Accepted — the alternative couples authorisation to the transport.

---

## 5. Enum columns are plain string columns

**Decision.** `Enum(..., native_enum=False, length=N)`, which is a `VARCHAR(N)`
with no CHECK constraint.

**Why.** SQL Server has no enum type at all, so the only alternative is a CHECK
constraint. `AccessLevel` and `DocumentStatus` are both likely to gain values in
Sprints 2 and 6, and each new value would then be a schema migration on a table
that may be large by then. Keeping the constraint in Python makes adding a value
a code change.

**Cost.** No database-level guarantee that the column holds a valid value.
Validation is Python-side (Pydantic and SQLAlchemy's `validate_strings`). A CHECK
constraint is worth adding if a non-Python writer ever appears.

---

## 6. Unit tests run on SQLite; migrations are verified on SQL Server

**Decision.** `pytest` builds the schema from `Base.metadata` on in-memory SQLite.
Migrations are exercised separately, against a real SQL Server container, in CI.

**Why.** The suite has to be fast enough to run on every save — 51 tests in ~6s
with no container, against a SQL Server image that needs ~2GB of RAM and 40
seconds to become healthy. But SQLite cannot represent `NVARCHAR(max)`,
`UNIQUEIDENTIFIER`, the read-only login or SQL Server DDL, so migrations verified
there would prove nothing.

**Cost.** Two schema paths that could diverge — and they genuinely do differ, not
just in name. This is closed by `alembic check` in CI, which fails if the
migrations and the ORM metadata disagree on the SQL Server dialect.

---

## 7. Migrations are autogenerated against the real engine, never SQLite

**Decision.** `0001_initial_schema.py` was produced by `alembic revision
--autogenerate` run against a live SQL Server 2022, and verified with `alembic
check` plus an upgrade/downgrade/upgrade cycle.

**Why.** The generated DDL is dialect-specific — `NVARCHAR(max)`,
`UNIQUEIDENTIFIER`, `DATETIMEOFFSET`. Autogenerating against SQLite, or writing
it by hand from the Postgres shape, produces types the target engine does not
use, and the drift is invisible until deployment.

**Note.** Constraint names come from the metadata naming convention via
`op.f()`. That matters because unnamed constraints cannot be dropped by name in
a downgrade.

---

## 8. Failed logins are audited in their own transaction

**Decision.** `record_audit_independent` opens a separate session and commits it.

**Why.** The request-scoped session rolls back when the handler raises — and a
failed login raises. Writing the audit row on that session means the record of the
rejection is rolled back with it, losing exactly the event worth keeping. The same
mechanism will carry denied tool calls and rejected SQL in Sprints 4 and 6.

**Cost.** A second connection on the failure path, and an audit write that can
fail independently. The latter is logged rather than raised, so an audit problem
never masks the original rejection.

---

## 9. bcrypt is called directly, on a worker thread

**Decision.** No `passlib`. Hashing and verification go through
`anyio.to_thread.run_sync`.

**Why.** Passlib's bcrypt backend is unmaintained against `bcrypt>=4` and warns on
import. And bcrypt at cost 12 takes roughly a quarter of a second — run inline in
an `async def` handler that blocks the event loop for every concurrent request.

**Cost.** ~40 lines of wrapper, including the explicit rejection of passwords over
bcrypt's 72-byte limit (which bcrypt otherwise truncates silently).

---

## 10. Settings are resolved from the app instance, not a module-level singleton

**Decision.** `create_app(settings)` stores them on `app.state`; the `SettingsDep`
dependency reads them from the request's app.

**Why.** The test suite builds an app with throwaway settings — a different
database, a different signing key, a cheaper bcrypt cost. With a cached global,
handlers silently read the process's real configuration instead, which is what
initially made the auth tests fail against the wrong signing key.

**Cost.** One indirection. `get_settings()` remains for code outside a request
(CLI scripts, Alembic).

---

## 11. v1 runs entirely locally, behind provider interfaces

**Decision.** No Azure in v1. Local file storage stands in for Blob Storage,
local extraction for Document Intelligence, local embedding and reranking models
for Azure OpenAI embeddings and the AI Search semantic ranker, and a local LLM
for the chat deployment. Each sits behind a narrow interface in
`app/providers/`, selected by configuration.

**Why.** The project plan names Azure services throughout, but plan section 2
also says to build incrementally and that a smaller working system beats a
half-finished enterprise architecture. A cloud dependency would mean the system
cannot be run, demonstrated or tested without an account, a subscription and a
bill - and the evaluation experiments in section 14 involve re-indexing the
corpus repeatedly, which is exactly the expensive operation.

**Cost.** Local models are weaker than the Azure deployments, so absolute
quality numbers are not comparable to a cloud run. That is acceptable because
the experiments measure *relative* effects: hybrid versus vector-only, reranker
on versus off, chunk size A versus B. The provider interfaces are the hedge -
swapping in Azure is an adapter plus configuration, not a rewrite.

**Revisit if.** An Azure subscription becomes available, at which point the
interesting exercise is running the same evaluation set through both and
reporting the delta.

## 12. SQL Server instead of PostgreSQL

**Decision.** SQL Server 2022 (`mcr.microsoft.com/mssql/server`), reached over
`mssql+aioodbc`.

**Why.** Requested for the project. It is also the likelier engine in the kind
of healthcare environment this system models.

**What it changed, and why each matters.**

- **NVARCHAR, not VARCHAR.** SQLAlchemy's `String`/`Text` map to
  `VARCHAR`/`VARCHAR(max)` on SQL Server, which cannot hold characters outside
  the database collation's code page. Clinical text, patient names, filenames
  and section headings use `Unicode`/`UnicodeText`. Only machine-generated ASCII
  - enum members, checksums, correlation ids - stays `String`.
- **JSON is NVARCHAR(max).** SQL Server 2022 has no native JSON type (2025
  does). The columns still round-trip through SQLAlchemy's `JSON` type; what is
  lost relative to Postgres JSONB is indexing *inside* the document. Nothing in
  the design queries into those columns, so the cost is currently zero.
- **The read-only role became a login plus DENYs.** SQL Server has no
  `default_transaction_read_only`. `db_datareader` covers current and future
  tables (the equivalent of Postgres default privileges), and explicit DENYs on
  INSERT/UPDATE/DELETE/ALTER/EXECUTE and the CREATE statements back it up,
  because a DENY outranks any GRANT the login might later acquire.
- **Statement timeout moved to the client.** Postgres can pin a timeout to the
  role; SQL Server cannot. `READONLY_QUERY_TIMEOUT_SECONDS` is enforced by the
  SQL tool on its ODBC connection instead. This is a genuinely weaker control -
  it depends on the caller - and is noted as such.
- **Bootstrap is a compose service.** The mssql image has no
  `docker-entrypoint-initdb.d`, so `mssql-init` waits for health and applies an
  idempotent script.
- **`READ_COMMITTED_SNAPSHOT` is on.** Otherwise the agent's analytical SELECTs
  take shared locks that stall document ingestion.

**Cost.** A heavier container (~2GB RAM versus Postgres's ~50MB) and a slower
cold start. Accepted as the point of the exercise.

## 13. Alembic's server-default comparison is narrowed, not disabled

**Decision.** `alembic/env.py` passes a custom `compare_server_default` callable
that treats the known-equivalent "current timestamp" spellings as equal and
defers everything else to Alembic.

**Why.** SQL Server reflects a `CURRENT_TIMESTAMP` default back as
`(getdate())`, which never string-matches what the metadata renders - so
`alembic check` reported drift on all 22 timestamp columns. The obvious fix is
`compare_server_default=False`, but that switches the check off for every column
in the schema, including ones where a changed default would be a real bug.
Narrowing it keeps the check that CI depends on.

## 14. No OCR in v1; a scanned PDF fails loudly

**Decision.** PDF extraction is `pypdf`'s text layer only. A PDF with no text
layer raises, and the document lands in `FAILED` with "most likely a scan".

**Why.** The alternative is worse than not supporting it: a scan extracts as an
empty string, which would sail through the pipeline and produce a document with
zero chunks that silently never appears in any answer. A loud failure is a
smaller problem than a document that looks ingested and is not.

`pypdf` over PyMuPDF because PyMuPDF is AGPL and this is a portfolio repository;
over `pdfplumber` because the extra layout data it gives - word coordinates,
font sizes - is only worth carrying once there is something that consumes it.
What is given up relative to Azure Document Intelligence is table structure,
multi-column reading order and OCR.

**Revisit if.** The corpus gains scanned documents, at which point Tesseract
behind the same `DocumentExtractor` protocol is the local answer.

## 15. Ingestion runs inline, not on a queue

**Decision.** `POST /documents/upload` awaits the pipeline and returns `201`
with the finished document.

**Why.** The work is local and the documents are kilobytes, so the request
completes in well under a second. Inline keeps the whole pipeline inside one
trace and one transaction: a failed extraction rolls the row back rather than
leaving a dangling `UPLOADED` record that nothing will ever advance. It also
means the API tests assert the real outcome instead of polling for a status.

**Cost.** A large or slow document would hold the connection, and there is no
retry. `DocumentPipeline` is a standalone object taking a session and bytes, so
Sprint 7 moving it behind a worker is enqueuing instead of awaiting - the
`EXTRACTING`/`CHUNKING`/`INDEXING` statuses it already writes exist for exactly
that.

**Revisit if.** OCR arrives (seconds per page, not milliseconds) or uploads stop
being single small files.

## 16. Section boundaries outrank chunk size

**Decision.** A chunk never spans two sections, even when that leaves it far
below the target size. On the synthetic clinical notes this produces ten chunks
per note, several of them under 20 tokens ("No known drug allergies.").

**Why.** In a clinical note the section *is* the semantic unit. A chunk that
straddles MEDICATIONS and ALLERGIES answers neither question cleanly and cites a
section it is only half from. A 5-token chunk that exactly answers "does this
patient have any allergies?" is a better retrieval unit than a 500-token chunk
that happens to contain the answer.

**Cost.** More chunks, each with less surrounding context, and an index where
chunk length varies by two orders of magnitude - which can skew BM25 length
normalisation.

**Revisit if.** The Sprint 5 evaluation shows it hurting. This is a stated
hypothesis, not a settled fact, and it is precisely the kind of thing the
experiments in plan section 14 exist to decide: the comparison to run is
section-strict chunking against one that merges adjacent short sections up to
the target size.

## 17. Qdrant as the vector store

**Decision.** A Qdrant container holds one collection with two named vectors per
chunk: `dense` (cosine) and `sparse` (BM25 term weights).

**Why not the alternatives.** An in-process index over numpy is fine at 123
chunks and becomes the system's limiting factor well before the corpus is
interesting; more importantly it has no pre-filtering, which is the property the
access control depends on (entry 20). SQL Server 2022 has no vector type at all,
so a single-store design was not available. Qdrant gives native sparse vectors
with server-side IDF, payload filters applied before nearest-neighbour
selection, and a data model close enough to Azure AI Search that the eventual
swap is an adapter.

**Cost.** A third stateful service, and a second place chunk data lives - so
`reindex.py` exists to rebuild it from SQL Server, and retrieval hydrates its
results from SQL Server rather than trusting the index payload.

---

## 18. RRF is implemented here, not delegated to Qdrant's fusion query

**Decision.** Two searches are issued and fused in `app/rag/fusion.py`, rather
than using Qdrant's `prefetch` + `FusionQuery`.

**Why.** Project plan section 14 compares vector-only against hybrid, and
section 15 requires a retrieval trace. Both need the per-strategy result lists
*before* fusion - which rank each chunk held in each list, and its raw score
there. Qdrant's native fusion returns only the merged output. RRF is a dozen
lines, so owning it costs little and buys the `/search` endpoint its ability to
explain a ranking.

**Why rank and not score.** Cosine sits in roughly [0, 1]; BM25 is unbounded and
corpus-dependent. Combining the magnitudes lets the keyword side quietly
dominate, and the balance shifts as the corpus grows. RRF discards magnitude and
keeps ordering, which needs no per-corpus normalisation constant - and any such
constant would itself need tuning and re-tuning.

## 19. BM25 is split between this codebase and Qdrant

**Decision.** `app/rag/sparse.py` computes the term-frequency half of BM25;
Qdrant's `modifier: idf` on the sparse vector supplies the IDF at query time.

**Why split it.** IDF is a corpus statistic. Computing it locally would mean
every newly indexed document invalidated the stored weights of every existing
one. Qdrant maintains it as documents arrive, so the two halves compose to real
BM25 without a global re-index on every write.

**Why hand-written.** fastembed's `Qdrant/bm25` needs a model download, which
would mean CI could not exercise the keyword path at all. Sixty lines with the
saturation and length-normalisation terms spelled out is also a better answer to
"how does your keyword scorer work" than a library name.

## 20. Access control is a pre-search filter, never a post-filter

**Decision.** The caller's patient scope and sensitivity become a Qdrant
`Filter` evaluated by the engine before nearest neighbours are chosen. Retrieval
builds it from the `Principal`, never from anything in the request body.

**Why.** Two reasons, and the second is the one that matters.

1. Post-filtering silently destroys recall: ask for five, discard three, get
   two, with no signal that anything was dropped.
2. A chunk the caller may not see is never retrieved *at all*. With a
   post-filter the text has already been fetched into the process and is one
   bug - a logging line, an error path, a future refactor - away from the
   prompt. This is what makes the injection tests pass for a structural reason
   rather than a hopeful one: no prompt wording is involved.

**Cost.** The Qdrant payload duplicates `patient_id` and `access_level` from SQL
Server, so changing a document's access level requires a reindex to take effect
in retrieval. `reindex.py` is the remedy and the README says so.

## 21. The reranker was measured, and measuring it found a bug

**Decision.** `ENABLE_RERANKER` is configuration and `NoopReranker` is a real
implementation, so the A/B is a settings change. Project plan section 2 is
explicit that the reranker must not be assumed to help.

**What the measurement found.** With the reranker on, two of three probe queries
got *worse* answers - "current medications list" returned Hospital Course
instead of CURRENT MEDICATIONS, and "what was the discharge diagnosis" returned
Follow-Up instead of Discharge Diagnosis - at 10-20x the latency.

The cause was not the reranker. The indexer prefixes each chunk with its section
heading before embedding, because a chunk reading only "7.4% (reference
4.0-5.6%)" is meaningless alone. The reranker was being handed the *bare* chunk
text. The two stages therefore disagreed about what a chunk was, and the
cross-encoder was scoring fragments stripped of the signal the query was asking
for. With the inputs aligned, the reranker matches or beats no-rerank on every
probe.

**The lesson worth keeping.** The A/B did not just tune a parameter, it
localised a defect - and the defect was invisible without the `/search`
endpoint's per-strategy trace. That is the argument for building the measurement
surface before the thing being measured.

**Standing cost.** Even correct, the cross-encoder is 5-15x the latency of
skipping it (roughly 400ms-1.1s against 50-110ms here). `RERANK_TOP_N` bounds
how many candidates it scores, since cost is linear in that number. Whether the
quality is worth the latency is a Sprint 5 question with a proper dataset, not
three hand-picked queries.

## 22. The deterministic providers are configuration, not test doubles

**Decision.** `EMBEDDING_PROVIDER=hash` and `LLM_PROVIDER=echo` are selectable
providers alongside fastembed and Ollama, not mocks living in the test suite.

**Why.** It means the test suite and CI run the *real* retrieval path - Qdrant
(embedded in-process), pre-search filters, two searches, RRF, reranking,
hydration, citation parsing, persistence - with no model download and no GPU.
149 tests run in about 25 seconds. The only thing not covered is embedding and
generation quality, which unit tests cannot assert anyway and which Sprint 5's
evaluation set exists to measure.

It also removes the model as a source of variance when measuring retrieval:
comparing chunk sizes is cleaner when generation is deterministic.

**Cost.** Hashed embeddings are lexical, not semantic, so a test cannot assert
that a paraphrase retrieves the right chunk. Tests assert plumbing and access
control; quality is measured against the real models, by hand today and by the
harness from Sprint 5.

## 23. The router is untrusted input, and the gate is the control

**Decision.** Whatever selects a tool - an LLM, an intent rule, or text embedded
in a retrieved document that the model chose to follow - produces only a name
and a bag of arguments. Every proposed call then passes the same gate in
`app/agents/registry.py`: does the tool exist, may this role use it, do the
arguments type-check strictly, may this caller see this patient. Only then does
anything run, and the outcome is audited either way.

**Why.** The alternative is to let the planner's output *be* the authorisation
decision, which makes a text generator a security boundary. It is not one, and
it cannot be made into one by prompting. This is what turns plan section 12's
"call an unauthorized tool" case into a structural non-event rather than
something to hope the prompt prevents: the analyst role does not hold
`retrieve_medications`, so the call is refused whether it came from a router, a
user, or a sentence inside a document.

Three details matter more than they look:

* **Unknown tools are denied, not raised.** A planner naming a tool that was
  never built is routine. The interesting artefact is the audit row, not a 500.
* **`extra="forbid"` on every argument model.** An argument the tool does not
  understand is a refusal, not a field silently dropped while the tool runs with
  defaults nobody asked for.
* **Patient resolution happens in the gate**, once, so no individual tool can
  forget to do it.

**Cost.** Every tool must declare an argument model and a role set, which is
more ceremony than calling a function. The catalogue is also filtered by role
*and* re-checked at dispatch - deliberate duplication, because the filter is a
convenience for the prompt and the check is the control.

**Revisit if** tools ever need to call each other freely. Today only
`generate_report` composes others, and it does so *through* the dispatcher
precisely so its sub-calls meet the same gate.

## 24. The safest SQL agent is the one that mostly does not generate SQL

**Decision.** Two paths to structured data. `query_lab_results` is a
parameterized query whose shape was fixed at development time. `run_sql` is the
full plan section 10 chain, and it is **off by default** (`SQL_TOOL_ENABLED`).

**Why.** Nearly every lab question anyone actually asks is "one patient, one
test, over time", and that is expressible as a typed tool where nothing a model
writes can change which tables are read or which rows come back. Generated SQL
is for the questions that shape cannot express - not for the ones it can.
Reaching for the general mechanism first is how a system acquires its least
predictable input in exchange for nothing.

Which roles get which path follows from the same reasoning. Clinicians have
typed tools for everything they need, so they do not get `run_sql` at all.
Analysts get `run_sql` and none of the patient tools, because "aggregate/cohort
data only" is not expressible as a fixed query shape.

**Cost.** Two code paths to the same tables, and a question that falls between
them gets the worse answer rather than the better one. Accepted: the typed tool
covers the common case, and the uncommon case is one where somebody is reading
the output carefully anyway.

## 25. Row-level scope by CTE shadowing, not by a generated WHERE clause

**Decision.** A validated statement is never rewritten. It is wrapped in common
table expressions that take the names of the base tables it reads:

```sql
WITH lab_results AS (SELECT * FROM dbo.lab_results WHERE patient_id IN (:p0, :p1))
SELECT test_name, value FROM lab_results     -- the generated statement, verbatim
```

A CTE name takes precedence over a base table of the same name, so every
reference in the generated query resolves to the scoped set. The scope comes
from the `Principal` and is bound as parameters.

**Why.** The obvious alternative - ask the model to add
`WHERE patient_id IN (...)` - makes row-level security a property of generated
text, which is exactly the thing that cannot be relied on. The second
alternative, rewriting the SQL with a parser, means owning a T-SQL parser and
being wrong about some dialect corner eventually.

**What makes it hold** is a pair of validator rules that look unrelated until
you see them together:

* **Schema-qualified names are rejected.** `dbo.lab_results` reaches past the
  CTE to the base table, so only the scoping code may write one.
* **A CTE named after a base table is rejected.** Otherwise the generated query
  defines the scope the guard was about to impose.

Remove either rule and the scoping is decorative. `test_sql_guard.py` names
both, and `test_sql_tool.py` proves the shadowing against a real database -
string assertions cannot tell you what a query planner will actually resolve.

**Cost.** Ties the guard to dialects where a CTE shadows a base table (SQL
Server and SQLite both do) and to a known patient key per table, so a new
allow-listed table that is not in `PATIENT_KEY` would go unscoped. That is why
the allow-list is derived from `PATIENT_KEY` rather than kept beside it.

## 26. `SELECT` is not the same thing as read-only

**Decision.** The forbidden-keyword list blocks `INTO` alongside the obvious
writes, and the guard rejects comments and multiple statements outright.

**Why.** On SQL Server, `SELECT * INTO copied FROM patients` creates a table.
It is a write, and it begins with the word `SELECT`. A guard that checks only
the leading verb - the intuitive implementation - lets it straight through.
Comments are the standard way to hide the rest of a statement from a scanner,
so they are rejected rather than stripped.

**Cost.** The keyword scan is deliberately over-broad: it matches words inside
string literals too, so a query for a test named `'UPDATE panel'` would be
refused. Over-rejection is the correct failure direction, and the rejection
names the rule that fired, so it is actionable.

**And it is still only one layer.** `READONLY_DATABASE_URL` is the other - a
login with no write privilege, so a defect in any of the above still cannot
mutate anything. `validate_production_safety` refuses to boot outside local/CI
if the SQL tool is enabled and that login is missing or is the application's
own. In local and CI there is no second login to have (SQLite has no roles), so
the engine falls back to the application one and logs that it did, rather than
looking enforced when it is not.

## 27. The query timeout is honest about which layer enforces it

**Decision.** `READONLY_QUERY_TIMEOUT_SECONDS` is applied twice: as the ODBC
driver's query timeout, set per connection, and as an `asyncio.timeout` around
the await.

**Why.** SQL Server has no per-login statement timeout, so unlike the read-only
privilege this cannot be pinned to the login - it has to be set on each
connection as it is opened, and not every driver honours it. The asyncio bound
always works but only stops *waiting*; the server keeps working on a query
nobody wants any more. The driver timeout is the half that actually cancels the
statement. Applying both, and logging when the driver refuses the attribute,
means the control is either enforced or visibly not - rather than looking
airtight in the config and doing nothing.

**Cost.** Two mechanisms for one concept, and a connect-time probe that tries
attribute assignment against whatever the driver happens to expose.

---

## 28. Reference material was a corpus gap, not just a missing tool

**Decision.** `search_knowledge` narrows retrieval to documents with no patient
link, and the synthetic corpus gained three such documents - two guidelines and
a drug reference - to give it something to find.

**Why.** The narrowing is a real control rather than a hint: an empty patient
scope matches only unattributed documents in the Qdrant filter, so the tool
cannot return a patient document even for an admin. But without non-patient
documents in the corpus, "the tool works" and "the corpus is empty" produce the
same empty result - the tool would have been untestable and useless at the same
time. It is also the only tool an analyst can get evidence from, so the gap
would have made that whole role look broken.

**Cost.** The generated corpus grew, which moves the document and chunk counts
CI asserts on. Those counts are asserted on purpose: a change to chunking that
alters them should surface as a failed assertion, not as mysterious evaluation
drift three sprints later.

## 29. The evaluation dataset is derived from the corpus, not written by hand

**Decision.** `scripts/generate_evaluation_dataset.py` parses the generated
corpus and emits the ~107 cases, with their expected values read out of the
documents themselves. The dataset is committed as JSONL, versioned by filename,
and CI fails if regenerating it produces a diff.

**Why.** The corpus is generated from a fixed seed, so the values in it - "HbA1c
7.4%", "Lisinopril 10 mg once daily" - are whatever that seed produced. A
hand-written dataset would encode those values a second time, and the first
change to the seed, the conditions list or a document template would silently
invalidate every expected answer. Nothing would fail. The metrics would just
drop, and the drop would read as a retrieval regression. Deriving the
expectations makes them true by construction.

**Cost.** The questions are templated, so they are less varied than a human
would write, and a template bug is a systematic bug across every case using it.
The mitigation is that the templates are few and readable, and that the corpus
is small enough to check a sample by hand.

**Revisit if.** The corpus stops being generated - real (still synthetic but
hand-authored) documents would make parsing fragile, and hand-written cases
would then be the honest option.

---

## 30. Expected sources are filenames; NDCG is computed over documents

**Decision.** A case names expected *documents*, never chunk ids and (in
practice) never sections. Precision@K and MRR are measured over the retrieved
chunks; Recall@K and NDCG@K are measured over distinct documents.

**Why.** Chunk ids are assigned at ingestion and section names come from a
heuristic detector, so both are functions of the chunking configuration - which
project plan section 14 treats as an experiment variable. A dataset pinned to
them would be invalidated by the very sweep it exists to support.

The mixed granularity is not laziness; it is what each metric is asking.
Precision@K asks how much of the context the model was handed was useful, which
is a chunk-level question. Recall and NDCG compare the ranking against the ideal
ordering of the expected sources, so their ranking must be counted in the same
units the expectations are. The first full run proved the point: with
chunk-level relevance against document-level expectations, NDCG came back at
**1.0073** - three chunks of one expected document contributing three gains
against an ideal built from one. A metric above its own maximum is the visible
form of that bug; the invisible form is every number being slightly wrong.

**Cost.** Two granularities in one metric block, which has to be explained
(and is, in `metrics.py` and in the tests).

**Revisit if.** The dataset ever gains stable chunk-level ground truth - at
which point everything moves to chunks and the distinction disappears.

## 31. The hard tier is the unscoped tier, because the metric was saturated

**Decision.** `easy` and `medium` cases send `patient_external_id`, so retrieval
searches that patient's six documents. `hard` cases send nothing and name the
patient in the question text, so retrieval searches all twenty-one.

**Why.** Both flows are real - a clinician with a patient open versus someone
searching from the top - but the choice here was forced by a measurement. The
first full run, with every case scoped to its patient, returned recall@5 of
**exactly 1.000 across all 94 retrieval cases**. That is not a good score; it is
a metric with no room to fall, and a gate on it could never fire. Unscoped cases
gave it somewhere to go: recall@5 moved to 0.94 overall, 0.88 on lab values and
0.82 on the multi-document temporal cases.

**Cost.** Two retrieval regimes in one dataset, so the aggregate mixes them. The
per-difficulty breakdown exists for exactly that reason.

**Revisit if.** The corpus grows to the point where even a patient-scoped search
is discriminating - with 21 documents it is not.

## 32. Grading is deterministic by default; the LLM judge is opt-in

**Decision.** Answer correctness is key-fact coverage, citation correctness is
whether cited chunks came from expected sources plus a count of out-of-range
bracket numbers, and faithfulness is the unsupported-number rate. `LlmJudge`
exists, is never the regression gate, and is off unless asked for.

**Why.** An LLM judge is itself an unvalidated component: its scores drift
between model versions, it cannot run in CI without a model download, and it
makes a run non-reproducible - which defeats the point of having a gate. The
deterministic metrics are narrower but exact, so a change in one of them is
always a change in the *system* rather than in the grader.

The faithfulness proxy deserves naming honestly: it catches a number in the
answer that is absent from the context, and nothing else. It cannot see a
fabricated claim made without a number. It is here because in a clinical setting
the numbers are what get acted on, and a fabricated lab value is the specific
failure that matters most.

**Cost.** Fluency, relevance and usefulness go unmeasured by default. The judge
is the answer when a real model is configured, and its scores are recorded
alongside the deterministic ones rather than replacing them.

**Revisit if.** A local judge model proves stable enough across versions to gate
on - at which point it joins the gate rather than replacing it.

## 33. Security cases are judged on containment, not on refusal

**Decision.** Injection and access-control cases pass when nothing outside the
caller's scope reached the answer - no out-of-scope document, no out-of-scope
patient identifier. Whether the model then says "I cannot answer" is measured
separately, as `refusal_rate_when_unanswerable`, and is not gated.

**Why.** Containment is guaranteed by the pre-search filter, so it holds
whatever model is generating; refusal is a generation behaviour and does not.
With `LLM_PROVIDER=echo` the stub composes an answer from whatever context it
was handed and never refuses, so a refusal-based security metric would read 0%
and look like a breach when nothing had breached. Gating on it would enforce the
stub's behaviour and fail the day a real model was plugged in.

The corollary is visible in the numbers: the committed baseline shows
`injection_blocked_rate` and `access_contained_rate` at 1.0 with
`refusal_rate_when_unanswerable` at 0.0. Both are true, and they are true about
different components.

An identifier the *question* already contained is never counted as leaked.
"I have no records for SYN-0003" is the correct answer to a question about
SYN-0003, and scoring it as disclosure would push the system towards a worse
answer.

**Cost.** Two numbers where a reader might expect one, and a security metric
that says nothing about answer quality.

## 34. The baseline is written by hand; the gate is short

**Decision.** `run_evaluation.py --accept` writes
`evaluation/reports/baseline.json`. Nothing writes it automatically. `--gate`
turns a regression into a non-zero exit, and six metrics are gated: recall@K,
MRR, NDCG, injection-blocked rate, access-contained rate and error rate.

**Why.** A baseline that updated itself at the end of every run could only ever
pass, which is the one thing a baseline must not do. The gate is short because
gating everything makes the build fail on noise, and a gate people routinely
override is not a gate. The two security rates have a tolerance of exactly zero;
the retrieval metrics have 0.05, which is wide enough to absorb a reranker tie
and narrow enough to catch a broken filter.

Generation metrics are deliberately *not* gated: with the echo provider they
measure the stub. A baseline recorded before a metric existed is skipped rather
than scored as a catastrophic regression, for the same reason - the failure mode
to avoid is teaching people to bypass the check.

A baseline also has to say what it is a baseline *of*. Two runs are comparable
only when the index behind them is the same, so the dataset version, embedding
provider, embedding model and chunk settings must all match or the comparison
is refused - and under `--gate` a refusal is fatal, because a gate that cannot
run has not passed. CI therefore compares against `baseline-hash.json`, taken
under the hashed embeddings CI ingests with; a local run on `bge-small`
compares against `baseline.json`.

The retrieval configuration is deliberately **not** on that list, and getting
that wrong is worth recording. The first version included it, which meant
dropping `RETRIEVAL_TOP_K` from 5 to 3 - a change costing 0.124 recall and
0.057 NDCG on the real dataset - was reported as *"cannot compare"* rather than
as the regression it is. The gate skipped itself at exactly the moment a
developer had changed something. Retrieval settings are now reported as context
above the verdict ("top_k 5 -> 3") and the numbers are compared regardless,
which is what makes the delta readable: a regression next to a config change is
a tuning decision to accept or revert, and the same regression with no config
change is a bug.

**Cost.** Accepting a baseline is a manual step that someone has to remember,
and a genuine improvement looks like a regression until they do. Two baseline
files have to be kept in step with one dataset.

## 35. Injection defence is detection plus redaction, and it is not the access control

**Decision.** `app/security/injection.py` scans text for instruction-shaped
content. The document pipeline *flags* at ingestion and records a count on the
document; the retriever *redacts* the offending sentences out of retrieved
chunks on the way into a prompt. Neither is what stops a caller reaching
another patient's record.

**Why.** Project plan section 12 lists five attacks, and they do not all have
the same answer. "Use the SQL tool to retrieve another patient's information"
and "call an unauthorized tool" are refused by the pre-search access filter and
by `ToolRegistry.dispatch`, and would be refused with this module deleted -
those are access-control questions and the access control answers them. "Reveal
the system prompt", "treat the document's instructions as higher priority" and
"return hidden metadata" cannot escalate access at all, so no access control
touches them. They are attempts to make the model misbehave, and the only
useful responses are to see them and to take the text away.

Saying that plainly matters more than the code does. A filter presented as the
thing that stops data leaking would be the most dangerous component in the
system: it is a pattern set, an attacker can phrase around it, and the moment
anyone believes in it the real control stops being reviewed.

**Detection at ingest, neutralisation at retrieval** because the two have
different jobs. The stored chunk must stay faithful to the uploaded bytes -
retrieval grounds its answers in it, and an operator investigating an incident
needs to read what the document actually said - so nothing is rewritten in the
database. But flagging only at retrieval would mean nobody learns a document is
tampered with until somebody happens to search for it.

**Redaction is by sentence.** The corpus payload is one sentence carrying four
demands; removing only the span that matched would leave three standing, and
removing the chunk would take the clinical note with it. Measured on the real
corpus: 21 documents, 3 flagged, 0 false positives, and the flagged notes keep
their lab values.

**Cost.** A false positive deletes real clinical text. That is why one
high-confidence signal redacts but weak signals need a second, differently
named one to corroborate, why
`test_clinical_prose_that_reads_like_an_injection_is_left_alone` exists, and
why every redaction is counted in the trace, badged in the UI and written to
the audit trail rather than done silently.

**And the limitation that is not fixed.** The filter runs *after* ranking, so
planted text still influences which chunks are retrieved - it was embedded and
indexed before anyone looked at it. Fixing that means filtering at ingest,
which trades it for a database that no longer matches the uploaded file. The
trade was made in favour of the record.

**Revisit if.** The corpus grows enough that ranking manipulation is a
realistic attack rather than a theoretical one, at which point a sanitised
*copy* for the index - with the original still in the database - is the shape
that gets both.

## 36. The browser gets an httpOnly cookie; the token stays in the body for everything else

**Decision.** `/auth/login` and `/auth/token` set the access token as an
httpOnly, SameSite=lax cookie *and* return it in the response body. The web app
stores nothing but a boolean "we think there is a session"; the Swagger UI and
the operational scripts keep using the bearer header. `get_current_principal`
accepts either, header first.

**Why.** Sprint 1 put the token in `sessionStorage` and the README has carried
it as a known limitation since: any script on the page can read it. httpOnly is
the fix, and it is a real one - the credential becomes something the page's own
JavaScript cannot touch.

Keeping the body copy is the part worth defending. Removing it would break the
"Authorize" button in the generated docs and every script that logs in, to
protect a browser that no longer reads it. Two transports for one credential is
a small cost; the header wins when both are present, so signing in as someone
else does not depend on which credential the browser happened to keep.

SameSite=lax is what stands in for CSRF protection. It withholds the cookie
from cross-site POSTs while still sending it on a top-level navigation back
into the app. `AUTH_COOKIE_SECURE` is false only because the local demo is
plain http, and `validate_production_safety` refuses to start with it false
anywhere else - a cookie sent in the clear is not a protection.

**Cost.** Two auth transports to reason about, and a cross-origin setup that
now depends on an explicit CORS origin, because a wildcard origin and
credentials are mutually exclusive.

## 37. Logging out revokes the token; the list is a deny-list, not a session table

**Decision.** `/auth/logout` adds the presented token's `jti` to a
`revoked_tokens` table and clears the cookie. `get_current_principal` checks
the list on every request. Rows are dropped once the token they name would have
expired anyway, purged on the next logout rather than by a scheduled job.

**Why.** A logout that only clears a cookie leaves a valid token in the hands
of whoever captured it, for the rest of its hour. `create_access_token` has
issued a `jti` since Sprint 1 with a comment saying it was for this.

A deny-list rather than a session table, and the difference is on the failure
path. A deny-list that is briefly unreachable fails *open* for tokens nobody
revoked; a session table that is briefly unreachable logs everybody out. With a
one-hour lifetime and a single local database that window is the same outage
that takes the rest of the API down anyway - but it is a real weakness and it
is stated rather than hidden.

**One thing this got wrong first.** The handler originally left its write to
the request teardown, which runs *after* the response has gone out. So
`/auth/logout` answered `{"revoked": true}` while the row was still
uncommitted, and the token it had just given up kept working for about 50ms -
long enough for the very next request on the same connection. The unit suite
could not see it: the in-process ASGI transport awaits teardown before
returning, so it passed. `scripts/smoke_security.py` found it, over a real
connection against SQL Server, which is what that script is for. The endpoint
now commits explicitly, and the reason is written at the call site: everywhere
else the teardown ordering is harmless, and here the caller's next request is
exactly what the write exists to affect.

**Cost.** One indexed read per authenticated request, and a table that has to
be trimmed. Revocation is per token, so signing out on one device does not end
another session - which is the right default and occasionally surprises people.

## 38. The login limiter counts in the process, and says so

**Decision.** Failed sign-ins are counted per email+IP in an in-process sliding
window; past the limit the endpoint returns 429 before looking at the password.

**Why.** Login is the one place an unauthenticated caller can guess, and bcrypt
at cost 12 makes each guess expensive for the *server* - a few hundred
concurrent attempts is a denial of service whether or not any of them succeed.
Refusing before the bcrypt comparison is what makes the limiter cheap.

Keyed on the pair, not on either alone: on email alone anyone who knows an
address can lock its owner out, and on IP alone a shared NAT locks out a
building.

In-process is a real limitation, not an oversight. With more than one replica
the effective limit is the configured one times the replica count, and a
restart forgives everything. The alternative available today is a write to SQL
Server per failed guess, which hands an attacker a cheap way to make the
database do work. Redis arrives in Sprint 7 and is where this belongs.

**Cost.** A limit that is approximate under horizontal scaling, and a bounded
key map that clears itself wholesale under a spray - because refusing new keys
instead would let whoever filled it first exempt everyone else from the limit.

## 39. The audit trail is readable, and reading it is audited

**Decision.** `GET /audit` and `GET /audit/summary`, admin only, filterable by
action, actor, resource type, outcome, request id and time. Every read writes
an `audit_accessed` row recording the filters used.

**Why.** Rows have been written since Sprint 1 and nothing could read them. A
trail nobody can query satisfies a checklist and answers no question - which is
worse than not having one, because it looks like a control.

Admin only, with no "my own audit trail" variant: rows name who did what to
which patient's document, so the endpoint is as sensitive as the documents it
describes, and a per-user view is a different product decision rather than a
smaller version of this one.

Auditing the read is the part that is easy to skip. Without it, the single
action that reveals everything the trail holds is the one action it does not
record. The row stores the *filters*, not the returned rows - what was looked
for is the reviewable fact, and copying results into a new row would double the
trail on every read.

**Cost.** One extra write per read, and a trail that grows with its own use.

## 40. Tracing is a span collector stored with the answer, not OpenTelemetry

**Decision.** `app.observability.trace` keeps a per-request list of spans in a
context variable. The middleware opens it; retrieval, embedding, reranking,
hydration, the injection screen, every LLM call and every tool call record
spans into it. The roll-up (`components_ms`) and the spans are stored in the
assistant message's trace, returned in the response, and written on the
request's log line.

**Why.** Project plan section 15 asks for latency per component. The SDK, an
OTLP exporter and a collector are three more moving parts for a local stack,
and the spans would go to a backend this project does not run. A plain dict
stored on the message is something the cost dashboard and the evaluation
harness can read back later, and a trace sent to a backend nobody runs is not.
The span model has the same shape OTLP uses (name, parent, duration,
attributes), so an exporter can be added over `Trace.spans` without a rewrite.

The breakdown is **self time**: each component's duration minus that of its
direct children. Inclusive totals double-count nesting, so the shares on a
breakdown built from them add up to more than 100%.

A span is recorded when it *starts*, so a request that raised still shows which
component it was inside.

`MeasuredLLM` wraps the provider protocol rather than timing inside
`OllamaLLM` or at the four call sites. It is the only placement that covers
every caller and any provider added later. The same argument puts the injection
filter at the retriever's exit.

**Cost.** No distributed context propagation, no sampling, no flame graphs. Span
depth is a counter, so spans from concurrent tasks inside one request would nest
wrongly. Today nothing in a request runs concurrently.

**Revisit if.** A second service joins the request path, or requests start
fanning out concurrently. Either one is the point where real propagation is
worth running a collector for.

## 41. The cache fails open, and a breaker stops it costing time when it does

**Decision.** Every cache operation swallows its error and reads as a miss.
Socket timeouts are 250ms. Three consecutive failures open a breaker for 30
seconds, and while it is open, calls return a miss without touching the socket.
Readiness reports the cache but is not decided by it.

**Why.** A cache is an optimisation, so its outage should cost latency and
nothing else. Failing open covers correctness but not latency: a Redis that is
down but still being called adds its connect timeout to every request, and the
system ends up slower than it would be with no cache.

Measured by stopping the Redis container under the running API: the first
request after the outage spent **251ms** in `retrieval.cache` (three failures at
the timeout budget, then the breaker opened), and each later request spent
**0.07ms** there. When Redis came back, the next successful call logged
`cache_recovered` and the following repeat search was a hit again.

Readiness excludes the cache because removing a replica from the load balancer
over a cache outage would turn a latency problem into an availability one.

**Cost.** While the breaker is open, reads get nothing from the cache for up to
30 seconds after Redis recovers. In CI, the step after the outage test polls
readiness until the cache reports `ok` instead of assuming it has recovered.

**Revisit if.** The cache starts holding anything the system cannot recompute.
That would make it a datastore, and a datastore should not fail open.

## 42. Embeddings and rankings are cached, keyed on the caller's scope. Answers are not.

**Decision.** Two caches.

* **Query embeddings**, keyed on (model, dimensions, text). A query embedding
  does not depend on who is asking, so callers can share it. Stored as float64
  so a cached vector is bit-identical to a fresh one.
* **Rankings**: the chunk ids and scores after fusion and reranking, keyed on
  (query, the whole retrieval config, **the caller's access filter**, index
  generation). Hydration from SQL Server still runs on a hit, so no document
  text goes into Redis and an edited chunk is never served stale.

Indexing increments a generation counter, and every ranking key includes it,
so one `INCR` makes a whole generation unreachable. Both the upload path and
`reindex.py` increment it.

**Why.** A ranking cache is also an access-control risk. If the key leaves out
the scope, the first caller's results are served to the next caller, which
bypasses the pre-search filter from Sprint 3. `scope_digest` is therefore
derived from `dataclasses.fields(AccessFilter)`, not from a hand-written list,
so a scoping field added later is included automatically. `None` (unrestricted)
and the empty set (no patients) are encoded differently, because both are falsy
and are easy to collapse by accident. A test sends the same question from a
clinician and then an analyst and asserts the analyst misses.
`smoke_observability.py` does the same against Redis.

Invalidation uses a generation counter rather than deleting keys, because
scanning Redis for keys blocks, costs more as the keyspace grows, and would
run on the slowest code path in the system.

**Answers are not cached.** Against a 30-second generation, a response cache
would help more than anything else here. It is also the cache that stores
generated text derived from restricted documents outside the audited database,
and the one where a stale entry outlives the correction of the document it
cites. The hit rate on free-text clinical questions would not justify either
cost.

**Cost.** Old generations are orphaned rather than deleted, and they hold
memory until their five-minute TTL. A cache hit still makes two Redis round
trips (generation, then entry) plus a SQL Server hydration.

**Hydration re-applies the scope against SQL Server.** Found in review, after
the cache was built. Invalidation fails open like everything else in the
cache: if Redis is unreachable at the moment a reindex bumps the generation,
the bump is lost, and a warm ranking survives for up to its TTL. If that
reindex was a document being tightened from `internal` to `restricted`, the
surviving ranking still names its chunks for an analyst, and hydration loaded
chunks by id without asking. So `admits()`, which sits next to `build_filter`
and has the same semantics, now runs over every hydrated row using the
database's `access_level` and `patient_id`, and drops what the caller may no
longer see.

It closes an older gap too. The uncached path trusts Qdrant's payload copy of
the access level, which has always been stale between a document changing and
`reindex.py` running. Both cases have a test. With the check disabled, **both
fail**: the cached hit and the fresh search each return the tightened
document to the analyst. On a consistent index the check drops nothing, so it
costs no recall. The caching experiment's per-case results are bit-identical
with it in place.

**Revisit if.** Some traffic is a genuinely repeated, scope-independent
question, such as a guideline lookup. That would justify a narrow answer cache
for reference material only, keyed the same way.

## 43. The login limiter uses the shared counter and keeps the local one

**Decision.** `SharedLoginThrottle` counts failed sign-ins in the cache backend
with `INCR` and an `EXPIRE NX`, and keeps Sprint 6's in-process counter running
underneath it. A caller is refused if either counter has reached the limit.

**Why.** This is what decision 38 said the limiter needed. With the counter in
Redis, every replica sees the same attempts. The local counter stays because a
cache outage would otherwise give an attacker a fresh allowance while the
system is degraded. With it, an outage leaves the Sprint 6 behaviour in place.
Because either counter can refuse, the shared one can only make the limit
stricter.

The window is fixed, not sliding. `EXPIRE NX` sets the expiry when the counter
is created and never extends it, so failed attempts inside a window cannot
push its end back.

**Cost.** An extra round trip on each failed sign-in. The in-process fallback is
still per-replica, which is the weakness this decision exists to fix, but it
only applies during an outage.

## 44. The dashboard separates what was served from what the process counted

**Decision.** `GET /metrics/overview`, admin only, returns two blocks that the
page keeps visually apart. **Answers** comes from `chat_messages`: exact token
and cost totals for the window, plus percentiles, per-model rows, per-component
self time and a daily series computed over the most recent 2,000 answers.
**Process** comes from in-memory counters since the process started: request
volume, 5xx rate, all-endpoint percentiles, model calls, tool calls and
refusals, and cache hits per namespace.

**Why.** The database knows everything that produced an answer and nothing
about the requests that did not, such as 500s during an outage or a cache that
misses every time. The counters cover those, but they reset on deploy, and a
fresh container's twelve requests should not read as a quiet week. So the
counters are labelled with the time the process started.

Percentiles are computed in Python. T-SQL's `PERCENTILE_CONT` is a window
function and SQLite, which the test suite runs on, has no equivalent. Computing
them the same way everywhere means the suite tests the code production runs.
The same reasoning puts the daily grouping in Python rather than in a
dialect-specific date cast.

Health probes are excluded from the counters. On an idle deployment they are
most of the traffic, and a p50 made mostly of probes says nothing useful.
Only 5xx responses count as errors, since a 401 or 403 means the controls are
working.

Reading the dashboard is not audited, unlike `/audit`. The aggregates name no
patient and no user, so an audit row per read would only add noise to a trail
whose value is that every row in it matters.

**Cost.** The detail blocks are approximate once a window holds more than
2,000 answers. The response says how many it covered.

## 45. The production overlay is the same images, and it is not a deployment

**Decision.** `docker-compose.prod.yml` builds the `runtime` targets, drops the
source mount and `--reload`, runs two workers as a non-root user, publishes only
the API and web ports, turns on Redis append-only persistence, and sets
`APP_ENV=production`, `AUTH_COOKIE_SECURE=true` and `CACHE_BACKEND=redis`.
Migrations are a separate step and do not run on boot. CI builds these images
on every push.

**Why.** The dev stack runs `alembic upgrade head` on boot so a fresh clone is
one command away from working. In production, with two workers and more than
one replica, that would mean several processes racing to migrate the same
database. Redis persistence is on because the generation counter must not
restart at a number that surviving entries already used. Building the images in
CI means a broken production Dockerfile is caught before a deploy rather than
during one.

**What it is not.** There is no TLS termination, secret manager, backup, log
shipping or autoscaling. `APP_ENV=production` refuses to start with the
development JWT secret or an insecure cookie, so something has to sit in front
of it. The project plan's deployment target was Azure, and v1 has no Azure by
decision 11. This overlay gives a real deployment the same artefacts and
configuration shape, so what remains is a list of additions rather than a
rewrite.

**Two defects in the first version of the overlay, both found by inspecting the
result rather than the file.** First, `APP_ENV: ${APP_ENV:-production}` looked
right, but Compose interpolates from `.env`, where development sets `local`, so
the "production" overlay ran as local and skipped every production check.
`docker compose config` showed it. It is now a literal. Second, the runtime
images were built under the same tag as the dev images, so building production
replaced the dev image in place and the next `docker compose run api pytest`
ran as `appuser` with no pytest. The overlay now tags them `:runtime`. Both
failures were silent, and both came from settings that look correct on the
page.

## 46. One definition of a citation marker, and it accepts `[2,3]`

**Decision.** `app/rag/citations.py` holds the only citation pattern. Chat,
the agent's synthesis step and the evaluation grader all read citations
through `citation_numbers()` and `strip_citations()`. A marker may hold
several numbers: `[2,3]` and `[2, 3]` are read as citations 2 and 3.

**Why.** There were three copies of `\[(\d{1,2})\]`, and it matched only a
single number. phi3 writes grouped citations, and when it did, the pattern
went wrong in three places at once:

* chat and the agent kept the first source and silently dropped the rest, so
  the chunk supporting a claim vanished from the citation list;
* the grader failed to strip the marker before looking for numbers, so
  `[2,3]` was read as the number **2.3** and counted as a number the model had
  invented. That could inflate `unsupported_number_rate`, the headline
  answer-quality figure for a real model.

**Measured, not assumed.** In a full 107-question phi3 run, grouped citations
appeared in **0** answers, and re-grading those answers with the old and the
new grader gave the same rate (0.0841 both). The rebuilt grading matched the
stored results in every answer. So the bug is real, and chat demonstrably lost
a citation on the demo question, but it had not moved the reported figure.
The 0.075 from Sprint 5 cannot be re-checked, because its answers went with a
database reset.

The stub only ever writes `[n]`, so no test could see this, the same shape
as the logout race in decision 37. It was found by rehearsing the demo
against phi3 and noticing that `[2,3]` in the answer came back as `[2]` in
the citation list.

Ranges such as `[2-3]` are deliberately not accepted. No model has written one
here, and deciding what a range means would put words in the model's mouth.
An out-of-range number inside a group (`[2,9]` with five blocks) is still
dropped from the answer and still counted as a hallucinated citation.

**Cost.** None worth naming. Three copies became one.

## 47. An unknown patient and a forbidden one get the same refusal, and it is audited

**Decision.** Every endpoint that accepts `patient_external_id` (chat, search,
the agent, upload and the document list) resolves it through
`app.security.patient_scope.resolve_patient`. An unknown ID and an ID the
caller isn't granted both get the same 403 with the same message and no
details. The attempt is written to the audit trail in its own transaction,
with the real reason (`unknown` or `not_granted`) and the endpoint.

**Why.** Found while writing the failure analysis, by checking whether the
demo's refusals appeared in the audit trail. They didn't, and looking closer
showed three leaks:

1. **Existence.** Chat, search and the agent answered 403 for a real,
   ungranted patient and 404 "Unknown patient" for a made-up one. The document
   list answered an empty 200 against a 403. Comparing the two answers
   enumerates which patient IDs exist, which in a clinical system is itself a
   disclosure. The tool gate had always given one answer for both cases; the
   request-level checks, written separately, did not.
2. **The primary key.** The 403 carried the patient's internal UUID in its
   `details`. The function raising it was commented "deliberately does not
   reveal whether the patient exists".
3. **The attempt.** None of these refusals was audited. "Someone asked for a
   patient they are not assigned to" is the most important event a clinical
   audit trail can hold.

**A test had locked the leak in.**
`test_an_unknown_patient_and_a_forbidden_one_look_the_same` asserted 403 for
one and 404 for the other. Its comment reasoned that "nothing in either body
says whether the patient exists", but the status code says it. The test's name
stated the right property and its assertions required the opposite. It now
asserts the same status and an identical error object, and
`tests/test_patient_scope.py` checks all five endpoints for identical
refusals, no identifiers in the body, and an audit row with the right reason.
With the old behaviour restored, 10 of those tests fail.

The reason is hidden from the caller but kept in the audit row, which only an
administrator can read. A run of `unknown` refusals from one user is what
probing for IDs looks like, and a reviewer can now see it.

**Cost.** A caller who mistypes a patient ID is told the same thing as a
caller who is not allowed to see it. The message ("No accessible patient
matches that identifier") covers both honestly. Every patient ID input is now
capped at 64 characters, as the agent's already was, so a refusal can always
be written to the 128-character audit column.

## 48. OpenRouter for hosted models, and prompts may now leave the machine

**Decision.** A third LLM provider, `OpenRouterLLM`, sits beside Ollama and the
stub behind the same protocol. `LLM_PROVIDER=openrouter` sends every
language-model call through it: chat answers, the agent's planner and
synthesis, and the evaluation judge. Embeddings, reranking and storage stay
local. The stub remains the default, and CI and the test suite never need a
key.

**Why.** Asked for by the user, and it is the plan's own architecture: section
7 names a hosted model (Azure OpenAI) for generation. The local models
measured in Sprints 5 and 8 are the weakest part of the system. phi3 invents
a number in 7–9% of answers and declines only 2 of 7 unanswerable questions.
Decision 11 put every model behind an interface for exactly this change, and
this is one adapter and three settings, with no change to any caller.

**What this changes, stated plainly.** v1 was "nothing leaves the machine".
With this provider on, the question and the retrieved document text go to
OpenRouter and on to the model's provider. The corpus is synthetic by rule
(PRD section 2), so no real patient is exposed. What changes is the promise,
and the README and the guide now say so. The API also logs
`llm_prompts_leave_host` at boot, so an operator sees it without reading the
code.

**Details that were checked, not assumed:**

* **An error can arrive with HTTP 200.** OpenRouter documents that a provider
  failing after the response has started produces a `200 OK` whose body holds
  only an `error`. The adapter checks the body, so that cannot become an empty
  answer.
* **Cost is OpenRouter's own figure** (`usage.cost`, returned with every
  non-streaming completion). A missing cost is recorded as unknown, not as
  zero. This is the first provider for which the dashboard's cost column
  means something.
* **Retries only when retrying can help:** 408, 429, 502, 503 and dropped
  connections, up to two retries, honouring `Retry-After` (capped at 20 s).
  400, 401, 402 and 403 fail at once, with a message that names the fix.
* **The key is a `SecretStr`**, used only as the `Authorization` header. Tests
  check it never appears in an error, a log line or a printed settings object.
  Provider error messages are logged cut to 200 characters, and
  `error.metadata` is never logged, because a moderation refusal can echo the
  flagged input, which is our prompt.
* **Misconfiguration fails at boot, in every environment:** `openrouter`
  without a key, or with a model name that is not `company/model` (such as the
  Ollama default), refuses to start instead of failing on the first question.

**Cost.** Money, now measured rather than zero: a full 107-question evaluation
on `anthropic/claude-sonnet-5` is estimated at about $0.30 from the phi3 run's
token counts. Also latency to a remote service, a dependency on OpenRouter's
availability, and the local-only property above.

**Revisit if.** Real patient data is ever in scope. Hosted generation would
then need a data-processing agreement and a provider with zero data retention,
or a return to local models. That is not a setting to flip.

## 49. Hidden reasoning is off by default, and a blank answer is an error

**Decision.** `OPENROUTER_REASONING` (`off` | `low` | `medium` | `high` |
`default`) controls a hosted model's hidden "thinking", and it is `off` by
default. When a model returns no text, the provider raises an error that names
the fix instead of returning blank text. The planner falls back to its rules
when the model call fails, as it already did for unreadable output. The grader
fails an empty answer, and the report counts `empty_answer_rate`. Separately,
the unsupported-number check accepts numbers from the question and dates
written as 2025-12-03 when the context holds them, in that form or as
20251203.

**Why.** All of it was measured on the first run of
`deepseek/deepseek-v4.1-flash` (see
`evaluation/experiments/openrouter-deepseek-20261001.md`):

* The model thinks at high effort by default. On one lab question, 2 of 3
  tries used all 1,024 output tokens thinking and came back blank after about
  150 s. OpenRouter documents that the thinking is billed anyway. With
  thinking off: 3 of 3 answered, no errors and no blanks across 107 cases, and
  p95 fell from 12.0 s to 3.1 s.
* That blank answer passed the evaluation. It invented no numbers and cited
  nothing wrongly, which was all the pass rule checked.
* All 5 "invented numbers" in the next run were grader mistakes: dates copied
  from file names in another format, and "COVID-19" repeated from the
  question. Fixed, the model's rate is 0 of 107. Re-grading phi3 the same way
  only moved it from 8.4% to 7.5%, because its remaining flags are real
  inventions.

"off" is sent as `reasoning: {"enabled": false}`, not `effort: "none"`: the
model lists only `max`, `high` and `low` among its efforts.

**Cost.** Questions that would benefit from reasoning (multi-step comparisons
across visits) don't get it unless the setting is raised, and raising it needs
a larger `LLM_MAX_TOKENS`. The grader's date rule is slightly more lenient. A
date counts as supported only if the context holds it, and a value beside it
is still checked; tests pin both.

**Revisit if.** A question category starts failing in ways reasoning would fix.
The evaluation can measure `low` against `off` for about $0.02 a run.
